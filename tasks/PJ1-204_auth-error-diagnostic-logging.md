認証 API の 500 エラーを Vercel のログから調査できるようにします。
秘密情報を記録せず、失敗した処理と原因を特定できる診断情報を残します。

---

## 📝 タスク名

*認証 API の安全な診断ログ追加と本番エラーの原因調査*（{{src/lib/auth/}}、{{src/lib/firebase/}}、{{src/app/api/auth/}}）

---

## 1. 背景・目的

1. Vercel 本番環境の {{/api/auth/signin}} と {{/api/auth/signup}} が 500 を返している。確認されたレスポンスは {{success: false}}、{{error.code: AUTH_INTERNAL}}、{{error.message: 認証処理に失敗しました}}。
2. {{src/lib/auth/signinHandler.ts}} と {{src/lib/auth/signupHandler.ts}} は例外を捕捉してレスポンスへ変換するが、元のエラーをログへ記録していない。このため Vercel のリクエスト一覧には 500 が表示されても、Messages に原因が残らない場合がある。
3. {{src/lib/auth/apiError.ts}} は未知のエラーを {{AUTH_INTERNAL}} に集約する。クライアントにはこの汎用的な契約を維持し、サーバー側でのみ診断情報を保持する。
4. 過去に {{firebase-admin → jwks-rsa → jose}} の読み込みで {{ERR_REQUIRE_ESM}} が発生した。{{package.json}} と {{bun.lock}} は {{jose@5.10.0}} へ変更済みだが、現在の 500 が同一原因かは未確定。依存関係の再変更や秘密鍵の変更を推測で行わない。
5. Firebase 側のログ閲覧を前提にせず、Vercel Functions の標準エラー出力で調査できる状態にする。外部ログサービスや有料プランへの変更は本タスクの前提としない。

---

## 2. 対象範囲と実装方針

1. 主対象は {{signinHandler.ts}}、{{signupHandler.ts}}、{{signin.ts}}、{{signup.ts}}、{{identityToolkit.ts}}、{{apiError.ts}}。{{sessionHandler.ts}} の 500 も同じ方針で記録する。
2. 認証は既存の Route Handler 経由を維持する。Server Actions、認証方式、レスポンスのエラーコード・ステータス、Cookie の設定方針は変更しない。
3. {{src/lib/auth/authDiagnostics.ts}} などにサーバー専用の共通ロガーを設け、{{console.error}} に単一の構造化 JSON を出力する。新しいログライブラリは追加しない。
4. 認証の各処理に診断用の段階情報を付与し、エラー変換前の情報を最終的な Handler で記録する。エラーの包み直しが既存の {{AuthNotConfiguredError}} 判定や Firebase エラーコードの分類を壊さない方法を選ぶ。
5. 原則として 500 に相当する障害を記録する。入力不備、誤ったパスワードなどの通常の 400／401 は障害ログとして大量出力しない。サインアップのロールバック失敗は別の障害イベントとして記録する。
6. 同じ例外を各層で重複記録しない。ロールバックなど別処理の失敗は同じ相関 ID で関連付ける。
7. {{.env.local}} の内容の確認・変更、Vercel の環境変数変更、依存ライブラリの再更新は本タスクの実装範囲外とする。調査に必要な変数は名前と設定有無のみを扱う。

---

## 3. 記録する診断情報

1. 記録項目を許可リストで定義する。{{event}}、{{timestamp}}、{{requestId}}、{{route}}、{{stage}}、{{httpStatus}}、{{publicErrorCode}}、安全に抽出した {{errorName}}／{{errorCode}} を基本項目とする。
2. {{requestId}} はサーバーで生成する。Vercel のリクエスト時刻・ルートとの照合手順を記載する。クライアント入力の相関 ID を無検証で採用しない。
3. 失敗段階を少なくとも次の単位で識別する。

   | 対象 | 段階の例 |
   | --- | --- |
   | サインイン | {{identity_toolkit.signin}}、{{admin.initialize}}、{{admin.verify_id_token}}、{{admin.create_session_cookie}}、{{cookie.set}} |
   | サインアップ | {{admin.initialize}}、{{admin.create_user}}、{{identity_toolkit.signin}}、{{identity_toolkit.send_verify_email}}、{{admin.rollback_delete_user}} |
   | セッション復元 | {{cookie.read}}、{{admin.initialize}}、{{admin.verify_session_cookie}} |

4. {{identityToolkit.ts}} では外部 API の操作名、HTTP ステータス、安全なサービスエラー識別子を保持する。現在の {{auth/internal-error}} への変換で失われる、API キー無効・制限、プロバイダー無効等の区別を可能にする。応答全文や任意の {{message}} は保存せず、既知の識別子の抽出または固定の診断分類に限定する。
5. Admin SDK の失敗では、秘密鍵の解析失敗・権限不足・認証情報不正等を安全なコードや固定分類で区別する。設定不足の場合は不足している環境変数名だけを記録し、値・長さ・断片を記録しない。
6. 生の {{Error}}、{{cause}}、{{stack}}、外部 API の応答や例外メッセージをそのまま出力しない。必要なスタック情報は、秘密情報を含み得る先頭メッセージと URL クエリを除去し、アプリ内のファイル位置に限定して件数・文字数を制限する。安全性を保証できない場合は省略する。
7. 既存の {{signup.ts}} のロールバックログも共通ロガーに置き換える。現在の UID と生の例外オブジェクトの出力を残さず、試行番号・上限・相関 ID・固定分類を記録する。

---

## 4. 秘密情報と API 契約の保護

1. パスワード、メールアドレス、UID、秘密鍵、サービスアカウント情報の値、Web API キー、ID／更新／セッショントークン、Cookie、Authorization ヘッダーは記録しない。
2. リクエスト本文・ヘッダー全体・環境変数全体・{{?key=...}} 付き URL を出力しない。{{fetch}} の例外メッセージやネストした {{cause}} にこれらが含まれる前提で設計する。
3. 予期しない型、循環参照、巨大な文字列、改行を含む値でもロガーが例外を投げたり、複数の偽ログを生成したりしないようにする。任意のエラーオブジェクトを展開・直列化しない。
4. ログ出力に失敗しても、元の認証エラーのステータス・レスポンスを変えない。
5. クライアントへ返す {{AUTH_INTERNAL}} のメッセージは維持し、内部の Firebase メッセージ・スタック・設定内容を返さない。相関 ID を公開レスポンスに追加する変更は今回行わない。

---

## 5. テスト・回帰確認

1. 既存の認証テスト構成を確認し、新規の共通ロガーと Handler の回帰テストは Vitest を使用する。既存の Bun テストは維持して実行する。
2. サインイン・サインアップ・セッション取得の予期しない失敗で、安全な診断ログが記録され、既存の API ステータスとエラー契約が維持されることを検証する。
3. 外部 API の拒否、ネットワーク例外、不正 JSON、トークン欠落、Admin SDK 初期化失敗、ロールバック失敗をモックし、失敗段階と安全な診断分類が区別できることを検証する。
4. 意図的に秘密情報を含む {{message}}、{{stack}}、{{cause}}、URL、任意プロパティを持つ例外を渡し、ログにも公開レスポンスにも秘密情報が含まれないことを検証する。循環参照、非 Error の throw、ロガー障害も確認する。
5. 成功時・通常の入力エラーでは障害ログが出ず、同じ 500 が重複記録されないことを確認する。
6. {{bun run lint}}、{{bun run typecheck}}、{{bun run test}}、{{bun run build}} を実行し、結果を記録する。Next.js に関わる実装前に {{node_modules/next/dist/docs/}} の該当ガイドを読む。

---

## 6. Vercel での確認と原因修正への引き継ぎ

1. ログ追加を含むコミットが対象デプロイへ反映されていることを確認する。Vercel の環境、デプロイ ID／コミット、再現時刻とタイムゾーン、対象ルートを記録する。
2. 専用の検証用アカウントで再現する。サインアップはアカウント作成・確認メール送信・ロールバックを伴うため、既存ユーザーへの影響を避け、試行回数を最小限にする。
3. Vercel の Logs で対象デプロイ・時刻・ルートを絞り、{{console.error}} の診断イベント、{{requestId}}、{{stage}}、安全なコードを確認する。Firebase Console のログは必須にしない。
4. {{AUTH_INTERNAL}} が返る一方でログがない場合、対象デプロイや表示フィルターを確認する。JSON 応答を生成する Handler 内の障害と、Handler 実行前の import／初期化障害を区別し、後者は Vercel の起動エラーを確認する。
5. 同じ {{ERR_REQUIRE_ESM}} が残る場合に限り、本番のインストール結果・キャッシュ・ロックファイル反映を調査する。新しい診断結果が得られるまで別の依存バージョンへ変更しない。
6. 原因が特定されたら、根拠となる安全なログ、対象箇所、必要な修正を実施結果へ記載する。認証障害そのものの修正は別タスクとして切り出し、このログ追加だけでログイン復旧済みとはしない。
7. 本番確認を実施できない場合は、ローカル検証済み範囲と本番の未確認項目を明記する。{{develop}}／{{main}}／{{master}} へのマージは同僚が行う。

---

## ✅ 完了条件（DoD）

- 認証 API の 500 について、Vercel で失敗段階・相関 ID・安全なエラー分類を確認できる実装と手順がある。
- {{AUTH_INTERNAL}} 等の公開 API 契約を維持し、内部情報をクライアントへ公開していない。
- 秘密情報・個人情報を含む例外のテストを通過し、既存のロールバックログにも生の例外や UID が残っていない。
- 既存の認証・Cookie・ロールバックの動作を維持し、関連テスト・型チェック・lint・本番ビルドの結果を記録している。
- Vercel の再現結果、または未実施であることと残作業が明記されている。原因修正の完了と診断ログ追加の完了を区別している。
- {{.env.local}} と環境変数の値を変更・資料へ転記していない。
