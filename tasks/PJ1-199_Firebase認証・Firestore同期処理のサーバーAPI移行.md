## タイトル

Firebase認証・Firestore同期処理のサーバーAPI移行

## 種別

Task

## 背景

- 認証処理（ログイン/ログアウト/セッション取得）がクライアント側で実行されている。
- Firestore同期（読み込み/更新）もクライアント側で実行されている。
- セキュリティ、監査性、責務分離、将来拡張の観点で、認証と同期の両方を API Route 経由に統一する必要がある。

## 目的

- 認証と同期の API I/F を定義し、サーバー側へ移行する。
- クライアントは UI と状態管理に集中し、データ更新・取得処理は API 経由に統一する。
- セッション管理をサーバー主導（httpOnly cookie）にする。

## 実装方針

- API Route 方式を主軸とする。
- 実装順は「設計 -> 認証API実装 -> 認証UI置換 -> 同期API実装 -> 同期UI置換 -> テスト/文書更新」とする。
- 競合解決は同期契約に従い、updatedAt 優先で判定する。

   参照: [PJ1-199-07*テスト更新と回帰確認*ドキュメント整備](tasks/PJ1-199-07_テスト更新と回帰確認_ドキュメント整備.md)

## 成果物

- 認証API: signup/signin/signout/session
- 同期API: sync upload/pull/state/run（契約に従う）
- クライアント認証層のAPI経由化
- クライアント同期層のAPI経由化
- テスト更新（単体/統合/E2E）
- READMEおよび運用ドキュメント更新

## 完了条件（Acceptance Criteria）

- 認証・同期の主要処理が API Route 経由で動作する。
- クライアントからの firebase/auth 直接実行が廃止される。
- クライアントからの Firestore 同期の直接実行が廃止される。
- セッションがサーバー管理され、リロード後も認証状態が復元される。
- 未ログインでも既存メモ機能が利用できる。
- 同期機能が既存要件（重複防止、差分反映、失敗件数表示）を満たす。
- 認証・同期のテストが安定して成功する。
- ドキュメントが新経路に一致している。

## 非スコープ

- Firestoreデータモデルの破壊的変更
- 認証プロバイダ追加（Google/GitHub等）
- 自動同期・リアルタイム同期の新規追加

## 想定リスク

- I/F曖昧さによる後続手戻り
- Firebase Admin と Cookie 設計不備
- 同期差分判定の漏れ、部分失敗時の再実行設計不備
- テストのフレーク増加
